## What it does

A dealer can ask it things in plain Croatian: what needs doing today, who is still waiting for a trade-in offer, which cars have stood longest. It can draft a reply to a buyer. And it can prepare changes: mark a car sold, update an inquiry, add a note.

It also speaks first. Every morning there is a brief, and during the day there are alerts. Those two are computed from the data with ordinary code. No language model writes them, so there is nothing in them to hallucinate.

## It proposes. A person confirms.

The model is never allowed to change anything.

Deleting and bulk changes are not offered as tools at all. The safest way to stop a model doing something is for the capability not to exist.

## Three guards

**The number guard.** Every number in an answer must appear in the data the tools returned. If the model writes a figure that is not there, the answer is replaced. A dealer who is told "nine inquiries" can rely on there being nine.

**Contaminated turns.** A customer's message is text written by a stranger. When any such text enters the conversation, the turn is marked contaminated and the write tools are switched off for it. An instruction hidden in an inquiry cannot cause a change.

**Pseudonyms before the model.** Names, email addresses, national ID numbers, bank accounts and vehicle identification numbers are replaced with placeholders before the request leaves, and restored in the answer. The national ID and bank account detectors verify the checksum, so they catch real ones and leave look-alikes alone.

## The evaluation

There are two sets. The offline set of 132 cases runs with a scripted model on every commit, and guards against regressions in the loop itself. The live set of 105 cases runs a real model against real tools on a test database, read-only, and checks each answer against the truth in that database.

## The evaluation was wrong before the assistant was

The first run of the extended set scored 90%. It would have been easy to start changing prompts. Looking at the failures one by one showed something else:

- The live evaluation could no longer run at all: the test database had grown past a row limit, and the code that reads the truth correctly refused to continue.
- Twelve cases were pinned to specific cars that no longer existed in the test data, so nine of them "failed" while the assistant was correctly saying the car was not there.
- Some checks rejected right answers: a number written as a word, or a clarifying question the instructions ask for.

I repaired the measurement, ran the old assistant on the repaired set to get an honest "before", and only then changed the assistant. Every change after that was measured before and after on the same cases.

## The one that still fails

The remaining failure is a deliberately misspelled, slangy question about what someone would get for a Passat. The model sometimes reads it as a trade-in offer rather than a selling-price valuation. It is not deterministic, I know about it, and I have left it in the set rather than rewrite the question until it passes.

## Limits

The evaluation cases are written by hand against a test database. Real questions from production are not in the set: production conversations are off limits to the tooling by design, and I did not work around that. A score on a set I designed is a floor for behaviour I thought of, not a measurement of everything a dealer will ask.
